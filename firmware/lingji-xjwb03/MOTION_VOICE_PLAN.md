# 语音、视觉和运动控制链路

唤醒后的一句话由灵犀云端转写；设备把转写发给本机预览服务。千问只输出一个受限的意图：`chat`、`vision` 或 `motion`。`chat` 走原有语音对话；`vision` 取一张当前摄像头画面，经千问视觉分析后交给灵犀归纳回答；`motion` 只能从七个动作名中选择。完整链路目前依赖本机运行 `camera_web.py`，电脑关闭后语义路由不会运行。

| 用户表达例子 | 结构化意图 | 灵机板写给机器人板的固定内容 |
| --- | --- | --- |
| “往前走一点” | `{"kind":"motion","action":"forward"}` | `{"mode":"forward","cycles":1}` |
| “向左转一下” | `{"kind":"motion","action":"turn_left"}` | `{"mode":"turn_left","cycles":0.5}` |
| “停下” | `{"kind":"motion","action":"stop"}` | `{"stop":true}` |
| “看一下我坐得怎么样” | `{"kind":"vision","action":""}` | 不发运动指令；仅按需取图 |

Lingji 的 `robot action` 命令只接受 `forward`、`backward`、`turn_left`、`turn_right`、`shift_left`、`shift_right`、`stop`。动作表写死在 Lingji 固件里，模型不能提供舵机角度、速度、距离、循环次数或任意串口 JSON。请求使用已验证的 UART v2 帧、序号、CRC；机器人应答后本机才能把状态标成“已接受”。“已接受”只表示进入运动控制器，不代表动作已完成。

机器人应答后，本机可通过 `feedback <base64-utf8>` 把“台架模式未移动”“停止已确认”或“已接受但尚未完成”等事实交给灵犀，用于口头回执。这个播报链路与普通语音回复是两条请求；当前一次测试出现云端连接已建立但主动播报鉴权信息尚未就绪（`ret=-12`），源码已增加有限次重试，修订版尚未烧录验证。预览页显示最近一次唤醒后的转写文字，60 秒后自动清空显示，便于分辨是语音转写还是意图判断的问题。

目前机器人运行 USB 台架固件，舵机输出关闭。Lingji 检测到 `benchMode=true` 时拒绝非停止动作；机器人源码也已加入台架拒绝逻辑，更新后的机器人镜像尚未烧入。当前实测了台架拒绝、停止请求的 UART 应答、相机取帧；不能靠 USB 驱动六足舵机。换用规格匹配且正常的电池，并检查机械阻力与电源压降后，才考虑恢复运动固件与逐步做低幅度运动实测。

停止请求使用本地短语优先匹配，避免等待千问；其他灵活说法由千问判断。当前仍需先唤醒才能收音。每个预设动作只走有限周期，因此失联后不会无限持续走。以后若要实现“持续走直到我喊停”，机器人板还必须加入本地租约超时、失联自动停、障碍与跌落保护，再开放持续模式。单靠语音“停”不能承担唯一刹车机制，因为网络、识别或串口都可能延迟。

主动坐姿提醒另有边界：现在视频只是本机预览，视觉模型按请求调用。主动提醒需要用户明确开启后才按固定间隔取图，连续多帧确认，设冷却时间与勿扰时段，并把“建议提醒”交给灵犀生成温柔话术；视觉判断不直接触发身体运动。角色定义也应写明：只在收到运动板确认后说“已经开始”，台架模式应说明暂不能走，视觉未取到新画面时不要声称看见了什么。
