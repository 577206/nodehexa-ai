## 编排

| 时间 | 身体 | OLED | 台词与停顿 |
| --- | --- | --- | --- |
| 0–1.5 s | 普通站姿 | 普通眼睛 | 0.2 s 开始“我好看吗？” |
| 1.5–2.7 s | 整机向一侧轻倾 6°，停顿 | 双眼变爱心 | 留出看清动作的时间 |
| 2.7–4.4 s | 缓慢倾向另一侧，停顿后回正 | 保持爱心 | 不用快速甩动 |
| 4.4–5.9 s | 六足保持 | 爱心放大、缩小两次 | 每次 0.75 s |
| 5.9–7.1 s | 小幅侧摆并轻扭一次，回正 | 右眼爱心眨一下 | 形成得意的小尾巴 |
| 7.1–8.1 s | 定住 | 得意眼睛 | 空出一秒让观众反应 |
| 8.1–10.8 s | 轻轻抬起姿态并保持 | 得意笑眼 | “好了，不用夸，我自己知道。” |
| 10.8–12 s | 恢复站姿 | 普通眼睛，双眼轻眨 | 收尾，适合接下一段 |

“歪头”用**整机侧倾**表达，驾驶舱和底盘刚性联动，不虚构独立脖子。侧倾角 6°只是本次预演目标值；不是实机已批准的运动参数。所谓抬起姿态由小幅俯仰表达，不额外增加颈部或升降机构。

眼睛遵循物料草案的一块 128×64 单色 OLED、约 29.4×14.7 mm 有效显示区；采用钟笑咪提供的 8×8 爱心像素，每只眼睛以整数像素缩放绘制。白色只是单色显示示意，不承诺真实屏幕亮度或面罩透光效果。粉色、金色等情绪先转译为图案、大小和节奏，若以后换彩屏再单独评估。

## 构建方法

先把表演做成一条固定时间轴；身体是姿态轨道，眼睛是 1-bit 图案轨道，台词是音频轨道。预演先检查角色感和停顿，再检查关节可达性，最后才接实机。

当前运动预设具有循环和随机入口，直接按名字拼接 `rotate_z → beat_sway` 不能保证本片的左右停顿和精确拍点。后续若通过审阅，需要把这个编排做成**具名、有限时长的本地表演预设**，明确入口、回站姿和完成状态。模型只选择表演名；本机定义眼睛和语音 cue，底盘保存已核验的轨迹，不开放任意关节角度。

实机同步不能只在电脑发包后开始计时，也不能把 ACK 当完成。应先准备音频和 OLED 帧，再以底盘实际启动事件或明确的启动握手建立统一时基；遇到拒绝、台架模式或中断，取消未执行 cue 并保留真实状态。当前项目接口不具有本片所需的全部启动/完成和屏幕能力，这部分未实现。台架、低电量和失联等已有门禁继续生效。

35 秒串场建议保留：我好看吗 → 偷看被发现 → 快夸我 → 生气跺脚 → 得意叉腰 → 招财收尾。但完整招牌动作本身约 12 秒，其余五段需压缩并删去部分台词，才能控制在约 35 秒；十段完整双句台词不能都塞进去。

## 其他动作的落地判断

- 偷看、害羞：先用眼珠偏移与整机轻微偏航表达，没有独立转头能力。
- 装死：用小幅下降、闭眼和静止表达，不实际翻倒。台词改成“可爱能量耗尽……”可避免与真实低电量状态混淆。
- 生气：先用眼睛、短促身体定格制造喜感；跺脚与抬腿留待单腿轨迹和五足支撑验证。
- 叉腰：当前前腿仍承担支撑。先用得意眼睛、小幅后仰和摆身表达；不要把双前腿同时悬空当作默认动作。
- 招财、假死机：需要新单腿抬起/放下轨迹。五足着地不自动证明稳定，还要验证实际重心、支撑多边形、力矩与中断后的落腿。
- 节奏灯：没有音量包络输入时只能叫预编排节奏动画；真实随音乐跳动需从音频提取包络并使用同一时间基准。

最推荐补充一个动作：**“被夸后努力绷住”**。先维持半眯的淡定眼睛 0.5 秒，随后眼睛弯成笑眼、机身轻轻摆一下，说“嗯，客观评价，我收下了。”它和招牌动作形成问答，角色感来自“想装淡定但忍不住”，无需新增抬腿机构。本轮只记录创意，未追加实现。

## 已完成的核对与限制

腿部安装点和四段长度读取自 `firmware/include/config.h`，IK/FK 关系参照 `firmware/src/leg.cpp`，角度界限参照 `firmware/src/servo.cpp`。没有采用旧 `workspace/pathTool/src/config.py`，因为其中机械参数与现行固件不同。

在 0–12 秒间每 20 ms 采样，共 601 个姿态、3606 次腿部求解。计算验证了所有目标可达、求解角度不超现行软件范围、六个脚尖目标固定；具体范围和脚尖数值误差见 `kinematic_checks.json`。这些只说明理想刚性模型在运动学上可表达，不能证明实体机器人能稳定完成。

**待验证**：真实重心及支撑稳定性；腿与机身/其他腿的碰撞；舵机载荷、速度和温升；电源带载；显示驱动和引脚；真实语音、OLED、底盘的同步与完成事件。没有开展实体机器人测试，没有声明整机安全验收通过。预演经审阅后，才进入上述后续工作。

交付文件已核对：MP4 为 1600×1080、H.264 + AAC、24 fps、12.000 秒，288 个视频帧；FFmpeg 完整解码无报错。GIF 为 800×540、96 帧，受 GIF 时间单位量化影响总长 12.01 秒。已检查六格图及视频版式、爱心和眨眼关键帧，图片文件校验通过；详见 [媒体核对记录](media_checks.json)。音色是临时样本，未对最终角色音色作审美验收。本次只新增本目录，既有固件修改与其他设计文件保留原状。

## 复现

本机环境：Python 3 + Pillow；Blender 5.2.0 LTS 的 EEVEE 实时渲染器；FFmpeg；macOS Tingting 临时语音。为缩短等待采用实时光影，材质和透明面罩效果不是验收对象。视频以 12 fps 渲染、24 fps 容器重复帧输出，没有插帧；足够评审本片慢动作，但细微眨眼最终应以真实 OLED 刷新验证。

从 `nodehexa-ai/` 执行：

```bash
rtk proxy python3 design/robot_theater/source/timeline.py
rtk proxy say -v Tingting -r 160 -o design/robot_theater/line_1.aiff '我好看吗？'
rtk proxy say -v Tingting -r 180 -o design/robot_theater/line_2.aiff '好了，不用夸，我自己知道。'
rtk proxy blender -b --python design/robot_theater/source/build_scene.py
rtk proxy blender -b design/robot_theater/theater_preview.blend -a
rtk proxy python3 design/robot_theater/source/compose.py
```

`.blend` 使用本目录相对的纹理序列；分享可编辑场景时须同时保留 `textures/`。配音只是临时节奏样本，不代表最终角色音色。
